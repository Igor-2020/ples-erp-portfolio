# Инженерный разбор Ples ERP

Этот материал показывает ход инженерного мышления на примере практической системы учёта небольшого магазина. Он описывает архитектурные решения, а не заменяет проверку исходного кода или эксплуатационные испытания.

## Offline-first

### Проблема

В розничной торговле временное отсутствие интернета не должно автоматически означать потерю введённой кассовой операции. При этом нельзя считать операцию переданной только потому, что сеть снова появилась.

### Решение

1. Приложение сохраняет операцию локально в Room.
2. Операция попадает в постоянную очередь Outbox.
3. WorkManager планирует фоновую отправку и повторы.
4. SyncEngine передаёт операцию Backend по HTTPS.
5. Backend обрабатывает запрос и возвращает подтверждение (ACK).
6. Приложение сохраняет подтверждённый статус операции.

### Почему это важно

- Локальная запись отделена от передачи на сервер.
- Повторная отправка не должна приводить к повторному применению одной операции: используется уникальный идентификатор и механизм идемпотентности.
- Статусы PENDING, PROCESSING, SENT, FAILED и CONFLICT позволяют различать этапы обработки.
- Восстановление связи не равно мгновенному завершению синхронизации: подтверждение учитывается отдельно.

### Ограничения

Офлайн-подход требует проверки конфликтов, восстановления после аварийного завершения приложения, миграций локальной базы, повторной отправки и поведения сервера. Успешный тестовый сценарий не гарантирует отсутствие всех ошибок в любой среде.

## Общий Backend API

Web Frontend, Android Cashier и Android Administrator используют общий серверный слой. Это помогает не дублировать бизнес-правила в каждом интерфейсе и сосредоточить авторизацию и проверку доступа на сервере.

Клиентский интерфейс не должен быть единственным местом, где проверяются права. Backend обязан самостоятельно проверять пользователя, роль и контекст магазина для каждой защищённой операции.

## Изоляция данных

В проектной модели используются центральные данные и отдельная SQLite-база магазина. Такая структура требует аккуратного выбора базы на сервере и обязательной проверки контекста доступа. Нельзя доверять одному только идентификатору магазина, присланному клиентом.

## Работа с ИИ-инструментами

ИИ использовался как помощник при создании и изменении кода. Это не отменяет необходимости формулировать требования, проверять архитектурные последствия, собирать проект, анализировать ошибки и тестировать реальные пользовательские сценарии. В портфолио не заявляется, что каждая строка кода была написана вручную.

## Следующие инженерные задачи

- Завершить отдельное демонстрационное окружение с синтетическими данными.
- Проверить сквозные сценарии от интерфейса до Backend.
- Подтвердить процесс резервного копирования и восстановления.
- Проверить ограничения доступа и обработку ошибок на демонстрационной конфигурации.
- Добавить реальные скриншоты и видео только после повторной проверки актуальных сборок.
